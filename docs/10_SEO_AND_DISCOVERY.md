# SEO and AI discovery

## Rendering, first, because everything else is worthless without it

**Every publication body, abstract, glossary definition, capability status, citation block
and reference list is present in the initial HTML response.** Server rendered or statically
generated. No critical content arrives by client-side fetch. A retrieval system that
executes no JavaScript must be able to read the entire corpus.

Progressive enhancement is permitted for the graph explorer, search, filter controls and
ledger sorting. None of those is critical content and each degrades to a rendered list.

**Test, not intention.** The build fetches every canonical URL with JavaScript disabled
and fails if the rendered word count is below 95 per cent of the enhanced word count, or
if any `[E]` claim's citation is missing.

Semantic HTML: one `<h1>` per page; `<article>` around the body; `<time datetime>` on
every date; `<cite>` on every reference; `<dl>` for the glossary; `<table>` with
`<caption>` and `<th scope>`. Headings descend without skipping a level, because the
heading tree is how a retrieval system segments a document. `verify_public.py` checks
`STR-02` and `STR-03` enforce this in the source.

`gen_seo.py --check` fails CI if any generated file on disk differs from what the register
would produce. A hand-edited sitemap and a stale register both fail here.

## Sitemaps

`https://neoai.myneogroup.com/sitemap.xml` indexes `publications`, `glossary`,
`capability`, `figures`, `indexes`, `platform`.

`https://mickaelmosse.ai/sitemap.xml` indexes `thesis`, `selections`, `notes-essays`,
`indexes`.

**Version-pinned archive URLs are excluded from every sitemap**, and `gen_seo.py` asserts
this on its own output rather than trusting its input.

**`lastmod` reflects a content change only.** Regenerating a build does not advance it,
which is why the value comes from the register and not from a filesystem timestamp. A
`lastmod` that moves without a content change is a false freshness signal and degrades
trust in every subsequent one.

## robots.txt

`Bytespider` is denied on both hosts. `CCBot` is **allowed** on
`neoai.myneogroup.com`: the earlier standard denied it because that host carried no
publication text, and under the current model it carries the entire corpus. The reason for
the denial went with the reason for the host. This is recorded so it is not later mistaken
for an error and reverted.

Filter parameters are disallowed. `/capabilities.json`, `/pdf/` and `*.svg` are explicitly
allowed.

The data room is untouched by anything here: gated, `Disallow: /` for everyone,
`noindex, nofollow, noarchive, nosnippet` on every response.

## Feeds

Atom 1.0. `/feeds/all.xml` plus one per category on the research host; `/feeds/thesis.xml`
and `/feeds/notes.xml` on the founder site.

Each entry carries title, an `id` set to the **permanent identifier route** rather than the
canonical URL, `published`, `updated`, author, category, and a summary containing the
abstract only. **Feeds never carry the body.** Setting the entry `id` to the identifier
route means a canonical move does not create a duplicate entry in every reader.

A MINOR version updates `updated`. A MAJOR version generates a new entry titled with the
version.

## llms.txt

A proposed convention that no major retrieval system has committed to honouring. It costs
one generated file and the downside is zero, so it exists, and it is generated from the
same index as the sitemap.

The structural requirement is the important part: **the blockquote intro carries the four
claim classes**, so that a system reading only the first two hundred words learns that this
corpus distinguishes evidence from intent.

**One deliberate omission.** `llms.txt` carries no summary of any paper beyond its abstract
and no key-findings section. A generated summary of a paper that reports no measurement is
exactly where a system inventing a finding would get it from.

## Linking

| Link class | Target | Failure |
|---|---|---|
| Outbound typed relations | 3 to 8 | fewer than 1 |
| Inbound typed relations, at the six-month review | 2 or more | 0 |
| Distinct glossary terms linked | 5 to 15 | 0 |
| Contextual links to other publications in body text | 2 to 10 | more than 15 |
| External primary-source links | at least 1 per `[E]` claim | any `[E]` claim with none |
| Links to the Capability Register | 1 per referenced key | any key without one |

**Anchor text is the exact title**, optionally prefixed with the identifier. Never a
truncation, never a paraphrase. `click here`, `read more`, `this paper`, `here` and bare
URLs fail the build at `verify_public.py` check `STY-04`. An anchor never carries a claim
the target does not make. Cross-host links carry a visible host indicator.

**First-occurrence linking.** The first occurrence of a defined term on a page links to its
glossary page; later occurrences do not. Applied by the build from
`registers/vocabulary.json`, never by an author. Exclusion zones: headings, the abstract,
the citation block, figure captions, code blocks, and any rejected-alternative callout.

## What must not be done

No keyword stuffing, no cloaking, no doorway page, no synonym page, no text spun to target
a query. The corpus competes on being worth citing.

**Nothing may be promised.** Not a ranking position on any timeline, not that AI systems
will cite the corpus, not that a migration preserves traffic, not any keyword-volume figure
presented as a forecast. Structured data produces eligibility for presentation features and
machine legibility, and nothing more.

## Two risks specific to this corpus

**The corpus is smaller than the register.** Six publications against nineteen registered
identifiers. Indexes render what exists, the roadmap names what is registered with no
dates, and no page presents a publication count as an achievement.

**The strongest page carries the least keyword surface.** The note on responsible capability
claims is the corpus's best text and nobody searches for it. That is acceptable. It exists
to be found by a reader who has already arrived, and to be the page a sceptical evaluator
reaches from any other. It is linked from every publication's method reference, from the
library index and from `llms.txt`, and it is not optimised for a query.
